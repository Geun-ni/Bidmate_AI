- **참여자:** 곽영래, 강보라, 이정근, 조용희

## 1. 주요 논의 및 결정 사항

### 1.1 공사·용역 유형별 참고자료 공유
- 곽영래가 일부 공사·용역 유형에 대한 **대표 공고번호 및 제출서류 목록**을 정리해 카카오톡 단체방 게시판에 공유함. 전체 유형을 포괄하는 자료는 아님.
- 제출서류 목록에 적힌 **제출기한은 그대로 적용하지 않고**, 실제 공고 및 기준에 맞춰 확인해야 한다는 취지로 논의함.
- 곽영래는 적격심사 서류 제출이 **개찰과 적격심사 사이**에 이루어지며, 실무상 제출기한을 개찰일로부터 약 1주일 후로 설명함. 공유된 적격심사기준 조항에는 해당 적격심사기준 **제8조(제출서류 등) 제2항**으로, 적격심사 대상자로 통보받은 자가 **통보서 접수일로부터 5일 이상으로 지정된 기일 내** 서류를 제출해야 한다는 내용이 표시됨. 따라서 **‘개찰일로부터 1주일’은 모든 공고에 적용되는 고정 규칙이 아니며**, 해당 공고의 적격심사기준과 실제 통보서에 지정된 기한을 확인해야 함.
- 제출서류에 대응하는 공고를 찾을 때는 공유한 **대표 공고번호 목록**을 참조하기로 안내함.

### 1.2 프로젝트 대상 공고 범위
- 공사·용역 공고 중 **적격심사 대상 공고를 우선 범위로 한정**하는 방향에 의견을 모음.
- 논의 과정에서 종합심사, 전자공개수의(제한적 최저가) 등 다른 계약·심사 방식도 언급되었으나, 이번 프로젝트에서는 적격심사에 집중하기로 함.
- 공고 유형별 적용 금액 기준 등 세부 범위는 대화에서 확정되지 않음.

### 1.3 공고 정정 및 데이터 갱신
- 최초 등록된 공고가 이후 정정될 수 있는지, 공고 데이터를 저장할 때마다 재확인이 필요한지 논의함.
- 곽영래에 따르면 정정공고는 드문 편이며, SRM 공고 화면에서 **‘공고가 정정되었습니다.’** 문구 및 **‘정정사유’**가 표시되는 사례가 있다고 설명함.
- 이정근이 이날 병합한 수집기에서는 **API 등록일시가 변경된 공고만 우선 재수집**하도록 구현함. 정정 감지를 위해 SRM을 추가 요청하지 않으며, 첨부파일 내용 변경 시 AI 분석 캐시를 무효화함. 이는 구현된 방식에 대한 공유이며, 실제 모든 정정 사례를 포착하는지는 별도 검증이 필요함.

### 1.4 프론트엔드 대시보드 진행
- 강보라가 대시보드 UI를 수정하고, **다크모드**와 공고 클릭 시 **상세화면으로 이동하는 동작**을 구현했다고 설명함.
- 변경사항은 우선 개인 브랜치 `feat/notice-dashboard`에 반영되었고, 이후 `main` 반영을 위한 PR을 진행함. 대화에서 이정근이 PR을 승인했다고 밝힘. **추가 공유 내용에 따라 React 프론트엔드 초안이 이날 `main`에 병합된 것으로 확인됨.**
- 프론트엔드 요구사항 문서: `docs/design/frontend-requirements.md`
  - 참고 링크: https://github.com/Geun-ni/Bidmate_AI/blob/feat/notice-dashboard/docs/design/frontend-requirements.md
- 곽영래가 내려받아 확인한 `index.html`에는 달력이 보이지 않았으며, 당시 최신 버전이 `main`에 반영되기 전이었을 가능성이 언급됨. **최신 UI에서 달력이 실제로 구현되었는지는 확인 필요.**
- 대화 당시 대시보드에 표시된 공고 데이터는 **실제 API 연동 데이터가 아닌 임시 데이터**로 설명됨. 강보라는 백엔드를 수정하지 않았다고 밝힘. 이후 백엔드 수집기가 `main`에 병합되었지만, **프론트엔드 화면과 실제 DB의 연동 완료를 의미하지는 않음.**
- UI에 대한 추가 개선 의견을 팀원들에게 요청함.

### 1.5 적격심사기준 파일이 없거나 누락된 경우의 대응
- 입찰메이트의 공고 상세 화면 **‘점수 계산’** 탭에서 `적격심사기준 미확보` 상태가 표시되고, **‘적격심사기준이 없어 점수를 계산할 수 없습니다’**라는 안내가 노출됨. 화면에는 공식 API 첨부파일에서 적격심사기준을 찾지 못했다는 설명이 표시됨.
- 논의의 핵심은 **공식 API 및 SRM 조회를 거쳐도 적격심사기준 파일을 제대로 확보하지 못한 경우**, 웹을 이용하는 **업체 사용자가 해당 파일을 직접 업로드**하고 AI가 그 내용을 분석하도록 하는 **대체 경로**를 추가하자는 것임.
- 이정근은 AI를 활용한 분석과 **적격·비적격 판단** 방향에 동의함. 강보라는 특히 **수집 과정에서 파일이 누락된 경우 수동 업로드를 차선책으로 제공**해야 한다고 제안함.
- **구현 시 구분할 상태:** (1) 공고에 기준 파일이 원래 없는 경우, (2) 공고에는 있으나 API/SRM에서 수집에 실패한 경우. 업로드한 파일의 공고 일치 여부 및 분석 결과의 검증 방식은 후속 설계 필요. 실제 SRM 조회 수행 여부는 화면만으로 확인할 수 없어 구현 과정에서 점검이 필요함.

### 1.6 GitHub PR 협업 규칙
- PR을 검토할 때 **Files changed**에서 변경 파일과 경로를 확인하고, 의도하지 않은 다른 팀원의 작업 영역 변경이 없는지 살펴보기로 안내함.
- 다른 팀원의 브랜치 또는 담당 영역을 부득이하게 수정했다면 **단체방에 알리기**로 함.
- 대화에서 **PR #17 승인** 및 **PR #18의 CODEOWNERS 추가**가 언급됨. 추가 공유에 따르면 **PR #18 CODEOWNERS 설정은 이날 `main`에 병합됨.**
- CODEOWNERS는 향후 PR 생성 시 리뷰어를 자동 지정하기 위한 설정으로 설명되었으며, **설정이 병합된 이후부터 적용**된다고 안내함.
- 자동 리뷰어 지정이 작동하지 않는 경우 팀에 알려 확인하기로 함.

### 1.7 이정근의 공고 수집기 및 서비스 DB 스키마 병합
- 이정근이 **1번 업무(자동심사 조건 확인)**에 해당하는 **SRM 공고 수집기(`backend/collector/`)**와 **서비스 전체 DB 스키마(`backend/db/`)**를 구현해 PR로 올렸으며, 추가 공유에 따르면 이날 `main`에 병합됨.
- **수집 대상:** 한전(`COM01`) 공사·용역 중 낙찰방법이 **적격심사**이고 **입찰참가신청 마감 전**인 공고. 이날 논의한 서비스 범위 축소가 수집 조건에 반영됨.
- **자동심사 조건 데이터:** SRM 투찰제한의 면허자격명·적격자격명·지역·주력분야와 자동/수동, AND/OR 설정을 저장함. **조회 실패와 제한 없음은 별도 상태**로 구분하며, 한전 담당자 이름·사번은 저장하지 않음. 업체별 실제 매칭·판정 로직은 아직 구현 범위 밖이며 관련 테이블만 준비됨.
- **금액 및 일정:** 예비가격 기초금액, 추정가격, 사정액(`approximateAmount`), A금액(`totalAAmt`), 순공사원가(`overHeadCostAmount`), 개찰일시를 수집·저장함.
- **첨부파일 및 원문:** 공고문·적격심사기준은 **Open API 첨부에서 우선 수집**, 없으면 SRM에서 보완하며 **수집 경로를 기록**함. HWP/HWPX/PDF 본문 텍스트 및 한글 수식 스크립트를 DB에 저장하여 AI 파트가 읽을 수 있도록 연결 지점을 정의함. **LLM 요약이나 AI 판정 자체가 구현 완료된 것은 아님.**
- **정정 및 수집 안정성:** API 등록일시 변경을 기준으로 재수집 대상을 선정하고, 첨부 내용 변경 시 AI 분석 캐시를 무효화함. SRM 차단 방지를 위해 **요청 간격 3초, 공고당 1회 수집, 차단 감지 시 중단** 정책을 적용함.
- **DB 구조:** 기존 데모용 `schema.sql`을 기준정보·업체·공고수집·문서분석·판정점수·서류/알림·추천 뷰의 **7개 영역별 파일**로 교체함. 초기화 명령은 `python -m backend.db.init_db`로 통일하며, 기존 DB에 다시 실행해도 데이터를 유지하도록 구현함. 테이블별 읽기·쓰기 모듈, 명명 규칙, 화면별 사용 테이블은 `backend/db/README.md`에 정리됨.
- **기준정보 시드:** 참고 엑셀 기준 **면허 3,629건, 자격 20건, 시군구 253건**을 반영함. 지역제한 엑셀의 시군구 코드 **162건**에서 빠진 앞자리 0을 복원하여 6자리 코드로 저장함(예: 춘천시 `011013`).
- **구현 확인 결과(이정근 공유):** 실제 공고 `E012608220`에서 면허 `A06`, 지역 충북, 사정액 `271,946,271`, A금액 `10,171,627`, 순공사원가 `131,079,269`를 확인함. 공고문은 SRM에서 보완 수집하고 적격심사기준은 API에서 확보했으며 **수식 4개**를 저장함. 최근 30일 API 공고 **1,724건 중 서비스 범위 957건**을 저장했고, 재초기화 후에도 **957건 유지**를 확인함. 정정공고는 등록일시가 변경된 공고만 우선 재수집하고 처리 표시가 해제되는 것을 확인함.
- **팀 협의 필요 사항:** AI 추출 결과(`document_extraction`, `evaluation_rule`, `required_document_item`)를 **AI 파트가 직접 저장할지, 백엔드가 검증 후 저장할지** 결정 필요(조용희 협의). **공고유형(`work_type`) 분류 규칙 및 대표 제출서류 목록 시드**는 곽영래와 협의 필요. `backend/db/README.md`의 **이름 변경 제안 7건**도 확정 필요.
