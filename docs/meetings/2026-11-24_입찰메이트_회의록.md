**추천 기준.** 곽영래는 참가자격을 충족한 공고라면 배점이나 제출서류가 아직 없어도 추천 목록에 표시해도 된다고 답했다. 이용자는 먼저 입찰 참가 가능 여부를 판단해야 하기 때문이다. 상세 화면에는 어떤 정보가 미확인인지 밝히고 재확인 시점이나 원문 확인 방법을 안내하는 방향이다. 수동심사 공고는 참가 단계부터 자격서류가 필요할 수 있다.

## 연동·배포 확인 자료

- **24일 API 명세(사진 4).** 공고 목록·상세·일정, 점수 계산, 계정·업체·관심공고 API를 프론트엔드에 공유했다. 점수 입력을 비워 두면 ‘미산정’으로 표시하고, 통보 뒤 정해지는 서류 제출기한은 기준서 원문 문구로 전달한다.
- **24일 배포 화면(사진 5~6).** 테스트 업체 대시보드에 진행 중 추천 7건, 확인 필요 5건, 7일 내 마감 5건이 표시됐다. 가파도 RE100 감리 용역 상세에서는 ‘참가 가능(1차)’, 공고문·기준서 확보 상태, ‘통보 후 지정’인 서류 기한과 근거 문장을 확인했다. 수치는 화면을 캡처한 당시 해당 업체 기준이다.
- **25일 처리 이력(사진 7~9).** 수집기에 `--with-llm` 옵션을 추가했다. 제출서류 항목의 `source_quote`는 판단 근거가 된 문장, `source_sha256`은 그 문장이 나온 첨부파일 버전, `updated_by`는 작성 주체(PARSER·LLM·USER)를 기록한다. 정정 전후의 근거를 비교하고 재실행 시 사람이나 LLM이 보완한 결과를 보호하기 위한 변경이다. 기존 DB 행은 유지하고 새 열의 값은 NULL로 시작한다.

## 남은 작업

- **공고 한 건의 전체 흐름 검증.** 실제 공고와 유료 API로 수집 → 추출 → 추천까지 확인하고, 제출서류와 산식을 원문과 대조한다. #26의 테스트와 #27의 회귀 비교는 각각 연동 동작과 배점 규칙을 확인한 결과다.
- **운영 기준 확정.** #27의 하루 한 건 제한을 리뷰한다. LLM 호출 실패 건의 다음 날 재시도와 상세 화면의 재확인 안내 시각은 논의됐으며, 실제 운영 일정은 추가 확인이 필요하다.
- **Q&A 연결.** DB 직접 조회와 RAG를 비교해 답변 방식을 정한 뒤 질문 API를 화면에 연결한다. 공고 정정 알림의 채널과 구현 일정도 열려 있다.
