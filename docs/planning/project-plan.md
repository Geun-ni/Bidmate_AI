# 입찰메이트 프로젝트 기획서

입찰메이트는 전기공사·감리 업체의 입찰 담당자가 회사 조건에 맞는 공공 입찰 공고를 찾고, 공고문과 첨부 PDF에서 자격·일정·평가 기준과 제출서류를 빠르게 확인하도록 돕는 서비스다. 전력 분야 입찰 공고는 공사 종류와 금액대에 따라 적격심사 기준과 제출서류가 달라, 소규모 업체의 공고 검토 부담이 크다.

## 기능 범위

| 우선순위 | 기능 | 범위 |
| --- | --- | --- |
| P0 | 맞춤 공고 추천 | 업체 면허·지역·희망 금액대와 공고 조건을 규칙으로 비교하고 추천 사유를 설명한다. |
| P0 | 공고 요약 카드 | 공고문과 첨부 PDF에서 사업명, 금액, 일정, 참가자격, 평가 기준을 추출해 근거와 함께 표시한다. |
| P0 | 제출서류 체크리스트 | 공고별 필요 서류를 추출해 업체의 보유 서류와 대조하고 준비 상태를 표시한다. |
| P1 | 공고 질의응답 | 검색 증강 생성(RAG)으로 공고 원문 조항을 찾아 인용한다. |
| P1 | 맞춤 공고 알림 | 신규·정정 공고를 이메일이나 텔레그램으로 요약해 전달한다. |
| P1 | 적격심사 예상 점수 | 기준별 배점을 규칙으로 계산하고 참고용으로 표시한다. |
| P2 | 정정공고 비교 | 공고 차수 간 변경 내용을 요약한다. |
| P2 | 서류 양식 초안 | 가상 업체 정보로 샘플 서류의 초안을 작성한다. |
| P2 | 용어 풀이와 낙찰 사례 요약 | 적격심사 용어를 설명하고 공개 낙찰 사례의 경향을 요약한다. 투찰 금액 추천은 범위에서 제외한다. |

첫 데모는 P0 세 기능을 연결해 시연한다. 시연 사용자는 전기공사업 면허를 보유한 가상 소규모 업체의 입찰 담당자다. 후속 기능은 P0 검증 후 일정과 인력에 맞춰 진행한다.

## 시스템과 AI 활용

공고 본문과 첨부 PDF에서 조건·일정·서류를 추출해 구조화하고, 룰 엔진으로 업체와 공고를 매칭한다. 생성형 AI는 문서 추출·요약, 추천 사유 설명, 답변 및 알림 문구를 담당한다. 지원 여부와 제출서류 준비 상태는 입찰 담당자가 최종 확인한다.

- 요약과 답변에는 원문 조항이나 첨부 문서의 위치를 인용한다. 근거가 없으면 `확인 필요`로 표시한다.
- AI가 추출한 금액·날짜·면허명의 형식을 규칙으로 검증한다. 자격 매칭과 예상 점수 계산도 룰 엔진에서 처리한다.
- 서비스 화면과 README에 참고용 서비스이며 법적 효력이 없고, 최종 확인은 공고 원문과 발주처 기준에 따른다고 안내한다.

| 계층 | 기술 후보 |
| --- | --- |
| 프론트엔드 | React 또는 빠른 시연용 Streamlit |
| 백엔드·저장소 | Python FastAPI, 초기 SQLite, 필요에 따라 PostgreSQL |
| PDF 파싱·생성형 AI | PyMuPDF 또는 pdfplumber, GPT 또는 Claude API의 구조화 JSON 출력 |
| 원문 검색·알림 | pgvector 또는 Chroma, 이메일(SMTP) 또는 텔레그램 봇 API |
| 배포·협업 | Docker, GitHub Actions, GitHub Projects |

기술 선택은 팀 협의 사항이다. 현재 가상 데이터 데모의 실행 방법은 [저장소 README](../../README.md)를 참고한다.

## 데이터 및 공개 기준

공개 입찰 공고·공개 샘플 양식과 가상 업체·서류를 사용한다. 공개 API나 공고를 수집하기 전에 접근 조건과 이용 약관을 확인한다. 업체 정보는 로컬에서 처리하고, 외부 LLM에는 공고 본문과 처리에 필요한 최소 조건만 전달한다.

내부 문서, 실제 업체 정보나 제출서류, 원본 대화는 공개 저장소에 포함하지 않는다. 공개 회의록에는 사업장과 내부 시스템을 식별할 수 있는 정보를 일반화한다. API 키는 로컬 `.env` 또는 GitHub Secrets에서 관리한다. 오픈소스 라이선스는 팀 합의 후 확정한다.

## 역할 분담과 협업

| 역할 | 주요 업무 | 저장소 산출물 |

| 기획 | 자격·적격심사 기준, 사용자 시나리오, 기능 범위와 일정 | `docs/planning/`, 회의록과 결정 기록 |
| 디자인·프론트 | 와이어프레임, 목록·상세 화면, 데모와 홍보 콘텐츠 | `docs/design/`, `frontend/` |
| 백엔드·데이터 | 공고 수집, DB, 룰 엔진, API, 테스트·배포 | `backend/`, 스키마와 API 명세 |
| AI·알림 | PDF 파싱, 구조화 추출, 원문 검증, 요약·RAG·알림 | `ai/`, 프롬프트와 추출 평가 결과 |

작업은 GitHub 이슈로 만들고 Projects 칸반으로 진행을 관리한다. 작은 단위로 커밋하고 팀원 한 명 이상의 리뷰를 거쳐 `main`에 병합한다. 회의 후 24시간 안에 공개용 회의록을 올리고, 주요 결정과 이유는 `docs/decisions/`, 시행착오는 `docs/devlog/`, 홍보 기록은 `docs/promotion/`에 남긴다. 첫 작업 브랜치는 [협업 방식 결정 기록](../decisions/2026-11-11-project-kickoff.md)을 참고한다.

## 홍보와 결과 확인

입찰·전기공사 커뮤니티와 동종업계 네트워크에서 베타 체험과 설문을 받고, 개발자 커뮤니티와 저장소 README에서 구현 과정과 데모를 공유한다. 게시 규정을 확인하고 사내 채널은 공개 가능 여부를 검토한 뒤 사용한다. 의견은 `feedback` 이슈로 정리하고 반영 내역은 릴리스 노트에 남긴다.

과정 기록에는 이슈·커밋·PR, 회의록·결정 기록·개발 일지, 홍보와 릴리스 이력을 포함한다. 결과는 작동하는 데모, 사용 안내와 영상, 베타 사용자·설문·인터뷰 건수, 게시글 반응과 외부 피드백으로 확인한다.

## 주요 리스크와 확인 사항

| 리스크 | 대응 |
| --- | --- |
| SRM API 접근 및 이용 조건 미확인 | 접근 권한·약관·키 발급을 우선 확인한다. 접근이 어렵다면 공개 샘플을 수동 수집하거나 나라장터 공개 공고로 시연한다. |
| 첨부 PDF 추출 오류 | 전기공사·감리 등 한두 유형부터 시작하고 정답 데이터로 필드별 정확도를 측정한다. |
| AI 오답으로 인한 판단 오류 | 룰 기반 매칭, 원문 인용, 근거 부족 표시, 사용자 최종 확인을 적용한다. |
| 기밀·개인정보 노출 | 샘플과 공개용 문서를 사용하고 PR 리뷰에서 확인한다. |
| 일정 부족과 적은 사용자 반응 | P0를 먼저 통합하고 여러 채널에서 베타 사용자를 모집한다. 반응이 적은 경우에도 결과를 기록한다. |

팀에서 추가로 확정할 항목은 역할 배정, LLM과 API 비용 조달, 오픈소스 라이선스, 채널별 게시 규정이다.
