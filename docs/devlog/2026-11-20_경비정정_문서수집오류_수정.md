## 3. 문서 수집 오류 2건

| 공고 | 원인 | 수정 |

| E012606980 | Open API 링크가 파일 대신 HTML(1,064 bytes, `\r\n<!DOCTYPE html`)을 돌려줌. 수집기는 받기만 하면 확보로 보고 SRM 보완을 하지 않음 | `doc_reader.document_problem()` 추가: 빈 응답·HTML·확장자(hwp/hwpx/pdf)와 다른 형식이면 이유 반환. `save_attachment()`가 이 경우 파일을 남기지 않고 `FAILED` 기록 → SRM 보완 |
| E012607149 | `[★필독] 공고문의 담당자 안내.hwp`(공백 제거 시 `공고 문의`도 `공고문의`)가 공고문으로 분류돼 SRM 보완을 건너뜀 | `doc_kind()`: `안내`·`담당자`가 들어간 이름은 공고문으로 보지 않음 |

### 재현 (확보 파일로 Open API·SRM 흉내, 네트워크 없음, 임시 DB)

### 회귀 확인

- `downloads/` 아래 hwp·hwpx·pdf 54개: 문제 판정은 E012606980 HTML 1건뿐. 검증 때 읽은 47개는 모두 통과하고 문단 수도 같음.
- 합성 입력: 빈 응답, BOM+`<html>`, `<!DOCTYPE html>`, `<?xml …><html>`, 확장자 hwp인데 텍스트 → 모두 실패 판정. hwp 이름의 HWPX(PK), hwpx 이름의 HWP(OLE) → 통과(기존처럼 형식 자동 판별).
- 파일명 2,477종(DB API 첨부 + 대표 공고 SRM 첨부): 분류가 바뀐 이름은 담당자 안내문 3종뿐(공고문 → 제외). 적격심사기준 분류는 변화 없음.
- 현재 DB에서 API 첨부에 안내문이 공고문으로 잡히던 공고 23건, 그중 공고문 후보가 안내문뿐이던 공고 8건(E012607011·E012607149·E012607244·E012607237·E012607542·E012607376·E012607831·E012607829)은 새 코드에서 SRM 보완을 시도한다. 현재 DB의 첨부는 E012608220 2건뿐이라 이미 잘못 저장된 첨부 행은 없다.
- `init_db` 두 번 적용(사본) 정상, 새 DB 스키마에 `overhead_cost_amount` 생성, `collect --help` 정상.
