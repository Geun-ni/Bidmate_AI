# 공고 분석 파이프라인 연결 검토

기준: 2026-11-23 `origin/main`의 DB 스키마와 `feat/pdf-extraction`의 제출서류 추출 코드.

## 현재 구현과 저장 위치

- `bid_document_content`는 첨부파일별 파싱 본문과 읽기 상태를 저장한다. 최신 `main`에는 산식 규칙 파서 결과를 나타내는 `rule_extracted` 열이 있다. `1`은 문제 없이 추출, `0`은 LLM 보완 대상, `NULL`은 판단 대상이 아니거나 아직 실행 전이다. 제출서류 추출 상태를 뜻하지는 않는다.
- 수집기는 공고별 산식 추출기 `refresh_evaluation_rules`를 이미 호출하고, 결과를 `evaluation_rule`에 저장한다. 일부 항목의 불확실성은 해당 행의 `verification_status=REVIEW`로 남는다.
- 제출서류의 최종 저장 위치는 `required_document_item`이다. 현재 `ai/` 코드는 별도 SQLite 스테이징 DB에 저장하므로 운영 스키마로 옮기는 연결 작업이 필요하다.
- `notice_analysis_cache`는 공고 단위의 공통 분석 상태만 가진다. 산식과 제출서류의 성공·실패를 독립적으로 나타내지는 못한다.

## 권장 순서

1. 수집·파싱 후 `bid_document_content.read_status`와 첨부 버전을 확인한다. 본문 자체가 없거나 파싱에 실패한 경우 재파싱 또는 OCR을 먼저 시도한다.
2. 기존 산식 추출기로 `evaluation_rule`을 채운다. 행이 없거나 `REVIEW`인 항목과 추출기의 문제 목록을 공고 단위로 기록한다.
3. 산식 LLM은 행이 전혀 없는 공고에서는 관련 공고문·적격심사기준 전체를, 일부만 불확실한 공고에서는 해당 절·표·주석·가격 구간과 기존 행을 함께 받는다. 근거 문구·첨부 ID·원문 버전을 확인하고 배점 합계, 산식 변수, 반올림 규칙을 검산한 후 저장한다. `VERIFIED` 행은 자동으로 덮어쓰지 않는다.
4. 제출서류는 `ai/rule_documents.py`로 후보와 근거를 만든 뒤 스테이징 DB에서 검토한다. 후보가 없거나 범위·조건이 모호한 공고만 LLM으로 보완한다. 결과를 현재 스키마의 `required_document_item` 필드에 맞춰 이관하고, 원문 근거와 조건을 다시 검사한다.
5. 수집 완료와 분석 완료는 별도로 표시한다. 분석 실패 또는 검토 필요 상태여도 수집 결과는 유지하고 재시도 대상으로 남긴다.

## 상태·검증 규칙

- 기존 `bid_document_content.rule_extracted`는 규칙 기반 **산식** 추출 결과로만 사용한다. `0`이어도 `evaluation_rule`에 일부 `REVIEW` 행이 남을 수 있으므로, 행 유무와 `verification_status`를 함께 확인한다. 원문 읽기 실패는 별도 `read_status`로 판단한다.
- 작업별 상태가 필요하면 공고번호, 작업 종류(`EVALUATION`/`REQUIRED_DOCUMENT`), 첨부 버전, 상태(`PENDING`/`DONE`/`REVIEW`/`FAILED`), 문제 코드와 시도를 저장하는 작은 작업 테이블을 별도로 설계한다. `notice_analysis_cache`는 두 작업을 모두 끝낸 뒤 공통 상태로 갱신한다.
- `UNVERIFIED`는 기계 추출 후 확인 전, `REVIEW`는 불확실하거나 충돌하는 결과, `VERIFIED`는 정해진 검증 절차를 통과한 결과로 사용한다. 행이 0개인 경우는 행 상태만으로 표현되지 않으므로 작업 상태에 남긴다.
- 제출서류 후보의 누락 여부는 행별 상태만으로 판단할 수 없다. 공고별 필수 절·별표·첨부 범위를 확인하고, 원문에서 특정할 수 없는 ‘별도 요청서류’는 구체 명칭을 지어내지 않고 안내 문구로 남긴다.
- 재수집·정정으로 첨부 버전이 바뀌면 이전 결과를 무효화하고 재분석한다. 최신 수집기는 첨부 버전이 바뀌면 LLM·사용자 수정 배점 행을 삭제한 뒤 규칙 파서를 재실행한다. 제출서류 결과의 재생성 정책은 별도로 정해야 한다.

## 담당자 합의가 필요한 연결점

- 산식 및 서류 결과를 AI 코드가 직접 DB에 쓸지, 백엔드가 근거·스키마 검증 후 쓸지 결정한다. 권장안은 백엔드 검증 후 저장이다.
- 용희: LLM 호출 조건, JSON 출력 스키마, 원문 근거 필수화, 실패 시 재시도·비용 기록을 정의한다. 산식 프롬프트와 제출서류 프롬프트를 분리하고, 제출서류용 기존 `ai/required_documents_prompt.txt`를 기준으로 시작한다.
- 운영 DB가 정해지기 전에는 스테이징 SQLite에서 검증하고, 이관 시 공고번호·첨부 ID 대응과 중복 저장 방지를 확인한다.
