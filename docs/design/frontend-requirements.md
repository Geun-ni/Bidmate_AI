## 3. 화면별 요구사항

### UI-01 메인 대시보드
- 데스크톱: 왼쪽 약 1/3에 업체정보 카드(수정 버튼)와 관심공고 달력, 오른쪽 약 2/3에 추천 공고 목록. 좁은 화면에서는 세로로 쌓는다.
- 업체 미등록 시 입력을 유도하는 빈 상태를 보여준다.
- 공고 카드: 판정 배지, D-day, 공고명, 공고번호, 발주처, 추정가격(한글 병기), 참가신청 마감·투찰 마감, 확인 필요 사유, 문서 확보 상태, 관심공고 별표.
- 판정: `MATCH`는 "참가 가능(1차)", `REVIEW`는 **"입찰참가자격 확인 필요"** 배지와 사유. `MISMATCH`는 기본 목록에서 제외한다.
- 공고 상태: 마감·정정·취소 공고는 투찰 가능 공고로 오인하지 않게 회색 처리하고 라벨을 붙인다.
- 필터: 관심공고만 보기, 판정 상태, 마감 공고 숨기기. 정렬: 마감 임박순(기본), 금액순.

### UI-02 업체정보
- 업체명(필수), 사업자등록번호(선택, 숫자 10자리), 본점 전체 주소(필수), 알림용 이메일(선택).
- SRM 지역그룹 → 시·군·구 종속 선택(둘 다 필수). 16개 그룹만 노출, 전남·광주는 `I(전남광주)` 안내.
- 일반 면허: 검색형 복수 선택, 면허별 등록번호·등록일자 필수.
- 제한경쟁입찰자격: 복수 선택, 등록번호·일자 받지 않음.
- 입력값은 "사용자 제공 정보"임을 안내한다.

### UI-03 상세 — 요약
- 상단: 공고명, 공고번호, 발주처, 상태, 별표, 입찰 진행 단계(참가신청 → 투찰 → 개찰 → 적격심사 → 계약), 주요 일정, 캘린더 추가.
- **문서 확보 상태**: 공고문·적격심사기준 각각 확보/누락. 누락 시 관련 탭에 빈 상태와 원문 확인 안내.
- 참가자격 판정표: 항목(면허·자격·지역·주력분야) / 공고 조건 / 우리 업체 / 판정 / 심사 방식(자동·수동) / 근거.
- 공고문 추가 조건: 확인 방법(개찰 후 확인, 업체 직접 확인, 원문 확인 필요) 표시.
- 적격심사 기준: 배점표, 낙찰자 결정 기준 점수.
- 모든 추출 정보는 원문 근거를 펼쳐 볼 수 있다. 근거가 없으면 "확인 필요".

### UI-04 상세 — 점수 계산 (회의 1안)
- 상단에 낙찰자 결정 기준 점수(예: 95점)를 고정 표시.
- 입찰가격 점수: 사용자 입력은 **입찰가격, 예정가격 2개**. A값은 공고문에서 자동 추출한 값을 출처와 함께 보여주며 사용자에게 입력받지 않는다.
- A값 또는 산식이 없으면 계산하지 않고 **"계산 보류 — 원문 확인 필요"**.
- 수행능력(시공경험·숙지도·경영상태), 가점/감점은 체크리스트. 입력하지 않은 항목은 0점이 아니라 **미산정**.
- 모든 항목이 산정된 경우에만 예상 총점과 기준 대비 차이를 표시. 아니면 "산정 보류".
- **투찰가격 추천 UI는 만들지 않는다.**
- 결과 옆에 "참고용 시뮬레이션, 낙찰 보장 아님" 안내.

### UI-05 상세 — 필요서류
- 입찰참가신청 / 적격심사 / 조건부 서류로 묶은 체크리스트, 진행률 바.
- 서류별 원문 근거, 조건부 서류는 조건 표시.
- 체크 상태는 브라우저에 저장(초안). 인쇄 버튼.

### UI-06 관심공고·달력
- 별표한 공고의 참가신청 마감, 투찰 마감, 개찰 일정을 월 달력에 표시. 날짜의 일정을 누르면 상세로 이동.
- 관심공고 상태는 브라우저에 저장(초안).

## 5. 상태 색 체계

| 의미 | 토큰 | 사용처 |
| --- | --- | --- |
| 참가 가능(1차)·확보·완료 | `--ok` | 판정 MATCH, 문서 확보 |
| 확인 필요·미산정·임박 | `--warn` | REVIEW, 수동심사, A값 없음, D-3 이내 |

## 7. 백엔드에 요청할 데이터 형식 (초안)

현재 `GET /api/demo`에는 아래 필드가 없다. 프론트는 `frontend-react/src/mocks/`의 목업으로 먼저 구현했다. 필드명은 협의 대상이다.

| 필드 | 설명 |
| --- | --- |
| `status` | `OPEN` / `CLOSED` / `CORRECTED` / `CANCELLED` |
| `schedule` | `applyStart`, `applyEnd`, `bidStart`, `bidEnd`, `opening` (ISO 날짜시간) |
| `judgment.overall` | `MATCH` / `REVIEW` / `MISMATCH` |
| `judgment.items[]` | `key`, `label`, `required`, `mode`(`AUTO`/`MANUAL`), `status`, `reason`, `source` |
| `documents` | 공고문·적격심사기준별 `status`(`OK`/`MISSING`)와 파일명 |
| `extraConditions[]` | `text`, `verify`(`AFTER_OPENING`/`SELF`/`SOURCE`), `source` |
| `criteria` | `passScore`, 배점 항목, 근거 |
| `priceScore` | `maxPoints`, `aValue`(없으면 `null`), `aValueSource`, `formula` |
| `requiredDocs[]` | `name`, `stage`(`APPLY`/`QUALIFY`/`CONDITIONAL`), `requirement`(`REQUIRED`/`CONDITIONAL`), `purpose`, `timing`, `method`, `condition`, `source` |
| `schedule.qualifyDue` | 적격심사 서류 제출기한 (FUNC-016) |
| `scheduleMeta.{일정키}` | `confirmed`(확정 여부), `source`(일정 출처). 정정 공고면 최신 일정과 변경 이력 |
| `attachments[]` | `kind`(공고문/적격심사기준/기타), `name`, `url`, `size`, `origin`(공식 API / SRM 추가 조회) (FUNC-018) |
| `capability.management` | 업종 평균 부채비율·유동비율, 재무비율 구간표, 신용등급 점수표, `verified` (FUNC-019) |
| `adjustments[].detail` | 등급형(`select`, 등급별 점수) 또는 횟수형(`count`, 건당 점수·상한·적용기간) (FUNC-022) |
| `revisions[]` (신규 요청) | 정정 차수별 서류 요구사항 변경 내역. 체크 재확인 요청에 필요 (FUNC-025) |

## 8. 실행 방법

```bash
cd frontend-react
npm install
npm run dev
```

`http://localhost:5173`을 연다. 기존 Python 서버(`python -m backend.server`, 8000번)를 함께 켜면 `/api` 요청이 그쪽으로 전달된다(초안은 목업이 기본).

배포 시 Python 서버가 React 빌드 결과(`frontend-react/dist`)를 제공하려면 `backend/server.py`의 정적 파일 경로 변경이 필요하다. **백엔드 담당과 협의 후 진행한다.**
