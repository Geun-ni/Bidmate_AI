## 1. 전제

| 항목 | 내용 |
| --- | --- |
| 기술 | React 18 + Vite, react-router. 팀 합의로 React 사용 |
| 데이터 | 목업을 걷어내고 **백엔드 API(`/api/…`)의 실제 데이터**를 쓴다. API 응답은 `src/lib/adapt.js`에서 화면용 모양으로 바꾼다 |
| 백엔드 | 프론트 담당은 **백엔드 코드를 수정하지 않는다.** 화면에 필요하지만 API에 없는 것은 7장에 정리해 백엔드 담당에게 요청한다. API가 생기기 전에는 화면에 '준비 중'으로 안내하고, 생기면 프론트 수정 없이 동작하도록 미리 만들어 둔다 |
| 사용자 | 입찰 경험이 적은 소규모 업체 (11-11 회의) |
| 톤 | SRM 운영 기관 입장의 공공 서비스. 신뢰감, 쉬운 안내 |
| 원칙 | 추천·점수·AI 답변은 **1차 검토와 참고용**이다. 최종 자격이나 낙찰을 단정하지 않는다 |

## 3. 화면별 요구사항

### UI-01 메인 대시보드
- 데스크톱: 왼쪽 약 1/3에 업체정보 카드와 관심공고 달력, 오른쪽 약 2/3에 추천 공고 목록. 960px 이하에서는 세로로 쌓는다.
- **왼쪽·오른쪽 열 맞춤**: 업체정보 카드 높이를 오른쪽 제목~검색 영역과 같게 늘려, 달력이 공고 목록(안내 문구)과 같은 높이에서 시작한다. 화면 폭·글자 크기가 바뀌면 다시 맞춘다.
- **왼쪽 칸 고정**: 화면 안에 다 들어가면 스크롤해도 고정, 화면보다 길면 고정을 풀어 페이지와 함께 스크롤한다(칸 안에 스크롤바를 만들지 않는다).
- 로그인 전·업체 미등록 시 등록을 유도하는 빈 상태(로그인 / 업체정보 등록 버튼).
- 요약 숫자: 진행 중 추천, 확인 필요, 7일 내 마감, 관심공고.
- 공고 카드: 판정 배지, D-day, **참가신청 시작 전이면 "신청 MM.DD 시작" 배지**, 공고명, 공고번호, 발주처(한국전력공사 ○○본부), 지역 제한, 추정가격(한글 병기), 참가신청 마감·투찰 마감, 확인 필요 사유, 정정 공고 안내, 문서 미확보 안내, 관심공고 별표.
- 판정: `MATCH`는 "참가 가능(1차)", `REVIEW`는 **"입찰참가자격 확인 필요"** 배지와 사유. `MISMATCH`는 기본 목록에서 제외한다.
- 상세 필터 「지역」: 지역 제한(전체 / 우리 지역 한정 / 지역 제한 없음) 옆의 **시·도 드롭다운**으로 보고 싶은 지역을 고른다. 공고 지역은 지역 제한이 있으면 그 광역, 없으면 발주 지역본부로 추정(예: 경기본부 → 경기). 건설본부·본사 부서·발주부서 미수집 공고는 「지역 미분류」.
- 필터·정렬(한 줄): `전체 / 참가 가능 / 확인 필요` · `★ 관심공고만` · `마감건 포함` · `조건불일치 포함` · 정렬(마감 임박순·금액 높은순). 노트북 폭에서도 한 줄에 들어가도록 촘촘하게.
- **검색**: 필터 아래, 안내 문구("추천 결과는 SRM 조건을 비교한 1차 검토…") 위. 공고명·공고번호는 서버 검색(`GET /api/notices?q=`), **발주부서**는 지금 목록(진행 중·관심공고)에서 함께 찾는다(마감 공고는 발주부서 정보가 없어 공고명·번호로만).
  - 입력이 멈추면 0.3초 뒤 검색, Enter 즉시, Esc·✕로 지움. 결과 수 표시, 결과에서 검색어 강조.
  - 기존 필터를 그대로 적용한다(필터 때문에 숨은 결과 건수는 따로 안내하지 않는다).
  - `마감건 포함`이면 참가신청이 끝난 공고까지 찾아(`include_closed=1`) 카드 아래 간단한 목록으로 보여 준다(20건씩 더 보기).
  - 검색어는 주소(`?q=`)에 남겨 상세에 갔다 돌아와도 유지한다.
- **스크롤 시 상단 축소**: 제목~검색 영역은 스크롤해도 상단에 고정되고 작아진다. 배치는 그대로 두고 글자 크기·여백·설명 문구만 서서히 바꾼다(작아질 때 0.45초, 커질 때 0.75초 감속). 동작 줄이기 설정이면 애니메이션 없음.
- **흔들림 방지**: 필터를 바꿔 목록이 짧아져도 페이지 높이를 유지하고, 스크롤바 자리를 늘 비워 두어(`scrollbar-gutter: stable`) 화면 폭이 바뀌지 않게 한다.
- 공고 상태: 마감·정정 공고는 투찰 가능 공고로 오인하지 않게 회색 처리하고 라벨을 붙인다. 마감 여부는 저장된 진행 상태가 아니라 날짜로 판단한다.

### UI-02 업체정보 (로그인 필요)
- 업체명(필수), 사업자등록번호(선택, 숫자 10자리 — 동료가 가입할 때 합류할 업체를 찾는 데 쓰임).
- **본점 소재지**: 주소 검색(다음 우편번호 서비스)으로만 고른다. 고른 주소의 시도·시군구로 서버가 SRM 광역·시군구를 정하고(`GET /api/reference/region-match`), 화면에 "매칭됨 / 매칭 실패"를 보여 준다. 직접 입력·지역 직접 선택은 없다(주소-지역 불일치가 생기지 않음).
  - 백엔드의 행안부 주소 팝업 중계는 개발용(`--dev`)이라 배포 화면에서 쓸 수 없어, 같은 형식(`juso: {siNm, sggNm}`)으로 다음 우편번호 결과를 보낸다.
- 일반 면허: 서버 검색(`GET /api/reference/licenses?q=`), 복수 선택, 면허별 등록번호·등록일자 필수.
- 제한경쟁입찰자격: 서버 목록(`GET /api/reference/qualifications`), 복수 선택, 등록번호·일자 받지 않음.
- 저장: 새 업체 `POST /api/companies`(만든 사람이 소유자), 수정 `PUT /api/companies/<id>`. 서버 오류 문구를 그대로 보여 준다.
- 소속 업체가 여럿(관리자 등)이면 수정할 업체를 고른다. 합류 요청이 승인 대기 중이면 안내한다.
- **업체 구성원**(소유자·관리자): 합류 요청 승인·거절.
- 입력값은 "사용자 제공 정보"임을 안내한다. 알림용 이메일 칸은 백엔드에 저장 필드가 없어 뺐다.

### UI-03 상세 — 요약
- 상단: 공고명, 공고번호, 발주처, 상태·D-day·판정 배지, 참가신청 시작 전 배지, 별표, 입찰 진행 단계(참가신청 → 투찰 → 개찰 → 적격심사 → 계약).
- 주요 수치: 추정가격, 기초금액, 참가신청 마감, 투찰 마감, 개찰, **A값**(0이면 "해당 없음" — 주로 감리·용역 공고).
- **적격심사 서류 기한**: 대상자 통보 후 정해져 날짜가 없으므로 "통보 후 지정" 배지와 기준서 원문 문구를 보여 준다(`GET /api/notices/<번호>/schedule`).
- 정정 공고면 정정 차수와 "원문에서 확인" 안내.
- **문서 확보 상태**: 공고문·적격심사기준 각각 확보 / 수집 전 / 미확보.
- 참가자격 판정표: 항목(면허·자격·지역·주력분야) / 공고 조건 / 우리 업체 / 판정 / 심사 방식(자동·수동) / 근거. 판정 규칙은 10장. 업체 미등록이면 조건만 보여 주고 등록 버튼.
- 공고문 추가 조건: AI 분석 결과가 아직 없어 "원본 문서에서 직접 확인" 안내.
- 적격심사 기준: 배점 API(`/evaluation`)의 기준 점수, 항목별 배점과 세부 항목, 원문 확인 필요 표시, 출처 기준서 파일명. 배점이 없으면 사유(기준서 없음·AI 분석 대기 등).
- **원본 문서**: 공고문·적격심사기준 파일 목록(형식·크기·출처). 파일 이름 또는 [다운로드]를 누르면 `GET /api/attachments/<id>`로 받는다. 이 API가 아직 없어 지금은 "아직 지원하지 않음 · SRM에서 받기" 안내.
- **"💬 이 공고에 대해 묻기"** 버튼(UI-09, 이 공고를 질문 기준으로).
- 캘린더 추가(.ics, 구글 캘린더).

### UI-04 상세 — 점수 계산 (회의 1안)
- 입력 칸은 **공고마다 다른 배점 규칙**(`GET /api/notices/<번호>/evaluation`)으로 자동으로 만든다. 계산은 서버가 한다(`POST /api/notices/<번호>/score`, 입력이 멈추면 0.35초 뒤 자동 계산).
- 상단 고정 요약: 계기판, 예상 총점(미확정이면 "현재까지 산정된 점수"), 낙찰자 결정 기준 점수, 기준 대비 차이 또는 남은 항목, "참고용 시뮬레이션" 안내, 입력값 저장.
- 입찰가격: 사용자 입력은 **입찰가격·예정가격 2개**. A값은 서버 수집값을 보여 주며 입력받지 않는다. A값·산식이 없으면 계산 보류. 산식 비율, 최저점·상한 적용 안내, 적용 산식 보기.
- 그 밖의 항목(수행능력, 경영상태, 숙지도, 가점·감점, 결격 등): 규칙 종류별 입력 칸(금액, 숫자, 해당/해당 없음, 보기 선택, 장비 체크, 개발실적 목록 등 21종).
  - **소분류 접기**: 첫 소분류만 펼치고, 제목 줄에 "n/m 입력"과 점수를 보여 준다.
  - **한 줄 배치**: 왼쪽 항목·점수, 오른쪽 입력. 긴 기준 문구는 "ⓘ 기준 보기"로 접는다.
  - 보기가 3개 이하·짧으면 한 줄 버튼, 많거나 길면 드롭다운(닫힌 상태에서는 앞…끝만 보여 "(3년 이상)" 같은 구분이 잘리지 않게).
  - **진행 중 점수**: 소분류·단원·상단 요약에 산정된 항목만 더한 점수를 바로 보여 준다(묶음 한도 안으로).
  - **"나머지 모두 해당 없음 (0점)"**: 가점·감점 묶음에서 남은 칸을 한 번에 0점으로 채운다.
  - 점수 자리 폭을 고정해 "미산정 ↔ 숫자"로 바뀌어도 옆 글자가 흔들리지 않게 한다.
- 입력하지 않은 항목은 0점이 아니라 **미산정**. 모든 항목이 산정된 경우에만 총점과 통과 여부.
- 숫자 칸: 범위를 넘으면 끝값으로 바꾸고 "최대 10점까지입니다." 말풍선(2초).
- 금액 칸: 세 자리 콤마, 한글 병기. 입력 중에는 앞자리 0을 지우지 않는다(100,000,000에서 1을 지우고 5를 넣으면 500,000,000). 칸을 벗어나면 정리.
- Tab 순서: 입력 칸만 차례로(기준 보기·산식 보기·용어 설명은 Tab에서 제외, 마우스로는 열림).
- **입력값 저장**: 로그인·업체 있으면 `PUT /api/companies/<id>/evaluation-drafts/<번호>`, 다시 열면 이어서.
- 배점이 없는 공고: 사유를 보여 주고, 업체가 적격심사기준 파일(hwp·hwpx·pdf, 20MB)을 직접 올리면 그 업체 계산에만 쓴다(`/uploaded-criteria`).
- **투찰가격 추천 UI는 만들지 않는다.**

### UI-05 상세 — 필요서류 (API 대기)
- 필요서류 추출(AI)과 조회 API가 아직 없어 "준비 중" 안내와 원본 문서 확인 안내를 보여 준다.
- 체크리스트 화면(준비/미준비/해당 없음/확인 필요, 필수 서류 기준 진행률, 인쇄)은 만들어 두었고, API가 생기면 연결한다. 체크 상태는 지금은 브라우저에 저장한다.
- DB의 `required_document_item` 단계(기본서류·자격증명·적격심사·감독부서)에 맞춰 묶음을 바꿀 예정.

### UI-06 관심공고·달력
- 별표는 로그인 사용자별로 서버에 저장(`/api/favorites`). 로그인 전에 누르면 로그인 화면으로. 마감된 관심공고도 목록에 남긴다(`마감건 포함`).
- 달력: 관심공고의 참가신청 마감·투찰 마감·개찰을 월 달력에 점으로 표시. 날짜를 누르면 그날 일정, 없으면 다가오는 일정.
- **일정 목록은 5개씩**, 6개부터 "‹ 1 / 3 › · 총 n건"으로 넘긴다. 마지막 쪽이 짧아도 넘기기 버튼 위치는 그대로. 일정 한 줄은 2줄 높이(출처는 마우스를 올리면).

### UI-08 로그인·회원가입
- 이메일·비밀번호(8자 이상) 로그인·가입. 세션은 백엔드 HttpOnly 쿠키.
- 가입 시 사업자등록번호로 기존 업체를 찾아 **합류 요청**(소유자 승인 전까지 대기). 새 업체를 만들 사람은 가입 후 업체정보 화면으로.
- 상단에 사용자 이름, 관리자 배지, 로그아웃.

### UI-09 AI 질문 패널
- 모든 화면 오른쪽 하단 "💬 AI 질문" 버튼 → 오른쪽 패널(휴대폰은 전체 화면). Esc·✕로 닫고, 페이지를 옮겨도 대화 유지.
- **처음 열 때 책임 고지 동의**(체크해야 시작, 브라우저에 기억):
  > AI 답변은 수집된 데이터를 바탕으로 자동 생성되며 정확하지 않을 수 있습니다. 답변을 근거로 한 입찰 참가·투찰 등의 판단과 그 결과에 대한 책임은 질문자 본인에게 있습니다. 최종 확인은 반드시 공고 원문과 발주기관(한전 SRM)을 통해 해 주세요.
- 입력창 아래 상시 고지, 답변마다 "참고용 답변 · 공고 원문 확인 필요".
- 공고 상세에서 열면 "📌 공고번호 기준"을 붙여 함께 보낸다. 목록으로 가면 전체 기준으로. 업체가 있으면 업체 ID도 보낸다.
- 추천 질문 4개(공고 기준 / 전체 기준), Enter 보내기·Shift+Enter 줄바꿈(한글 조합 중 Enter 무시), 답변 대기 표시, 근거가 오면 "근거: 공고명"(누르면 이동).
- `POST /api/qna`가 아직 없어 "AI 답변 기능은 준비 중" 안내가 답변 자리에 나온다.

## 8. 실행 방법

### 로컬에서 보기 (개발 서버)

```bash
cd frontend-react
npm install
npm run dev
```

브라우저에서 `http://localhost:5173`을 연다.

- 화면의 `/api` 요청은 기본으로 **팀 배포 서버**(`https://211-233-216-208.sslip.io`)로 전달된다(`vite.config.js`의 프록시). 로컬에 백엔드나 DB가 없어도 실제 공고 데이터로 동작한다.
- 로컬 백엔드(`python -m backend.server`, 8000번)를 쓰려면 `frontend-react/.env.local`에 `BIDMATE_API=http://127.0.0.1:8000`을 적고 개발 서버를 다시 켠다.
- 계정 없이 보려면 `.env.local`에 `VITE_TEST_LOGIN=1`을 적으면 **「🧪 자동로그인 (테스트)」** 버튼이 생긴다(6장). 기본은 일반 로그인만.

### 서버에 반영하기 (배포)

`main`에 합치거나 GitHub에 푸시해도 **서버에 자동으로 반영되지 않는다**(자동 배포 설정 없음). 서버는 nginx가 `/var/www/bidmate` 폴더의 빌드 결과물을 화면으로 보여 주고, `/api/…`만 백엔드(127.0.0.1:8000)로 넘긴다(`deploy/nginx-bidmate.conf`).

1. 빌드: `cd frontend-react && npm ci && npm run build` → `frontend-react/dist` 생성
2. 서버에 올리기: `dist` 안의 파일 전부를 서버의 `/var/www/bidmate`로 복사(기존 파일 교체). 서버 접속 권한이 필요하므로 서버 담당(백엔드)이 진행한다.
3. 확인: 배포 주소를 새로고침해 화면이 바뀌었는지 본다. 화면은 같은 주소의 `/api`를 부르므로 따로 설정할 것은 없다.
