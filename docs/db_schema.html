2026-11-23

표 1개 추가(company_uploaded_criteria), 칸 2개 추가(collect_run), 규칙 보강으로 배점 숫자 바뀜.

표바뀐 점
company_uploaded_criteria표 추가: 업체가 직접 올린 적격심사기준 (zip 이거나 수집기가 기준서를 못 찾은 공고). 올린 업체만 쓰고 공용 evaluation_rule은 안 건드림. 원본 파일은 저장 안 하고 본문 + 규칙 추출 결과(rules JSON)만. 업체·공고당 1건, 공용 배점이 없는 공고에서만 점수 계산에 씀
collect_run칸 추가 rule_checked_count·rule_extracted_count: 수집 1번마다 배점 규칙을 돌린 공고 수와 그중 규칙으로 다 뽑은 공고 수 (성공률이 떨어지면 새 문장 표현)
evaluation_rule규칙 보강(원문 대조 3건 수정 + 감리 가감점 5종)으로 공고 159건, 2,563행. REVIEW 137행 → 21행
input_key 추가: bonus_ratio(교육훈련: 이수인원 ÷ 평가대상인원 × 점수), tech_dev(개발실적: 건별 목록). bonus_count는 'N월마다 X점씩'이면 parameters.period로 기간 입력
parameters 추가 키: special(OF전기원처럼 따로 세는 인원), short_tenure(단기 재직 감액). 배점 API는 source_quote를 내보내지 않고 출처 파일명만 줌
bid_document_contentrule_extracted: 기준서 175개 중 1이 151개, 0이 24개 (신청 가능 공고 169건 중 146건 규칙 추출)

2026-11-22

표 추가·삭제 없음. 칸 1개 추가(bid_document_content.rule_extracted), 바뀐 정의 1곳, 실제로 쓰기 시작한 표 6개.

표바뀐 점
bid_document_content칸 추가 rule_extracted: 적격심사기준 본문마다 규칙 파서로 배점·산식을 다 뽑았는지. 1 = 다 뽑음, 0 = 못 뽑은 게 있음(LLM 대상), 비어 있음 = 기준서 아님(공고문 등). 기준서 175개 중 1이 129개, 0이 46개 (공고 기준 126건 · 45건)
evaluation_rulerule_type에 GROUP 추가 (분야·묶음 행, max_score = 묶음 한도, 가감점 묶음은 {"min", "max"}). 하위 항목은 parent_id로 연결. 공고 159건, 2,539행 저장
rule_extracted=0 공고 처리: 항목 하나만 못 읽음(계산 방법이 문장뿐인 가감점, 양성실적, 기준비율 값 없음) → 행은 남기고 그 행만 verification_status=REVIEW (33건, 137행) / 배점표 자체를 못 믿음(PDF·zip, 금액 구간 불일치, 합계 안 맞음, 표 못 찾음) → 배점 행 없음 (12건)
LLM 대상 = rule_extracted=0 이면서 배점 행이 없거나 updated_by=PARSER·REVIEW 행이 남은 공고. LLM이 넣거나 고친 행은 updated_by=LLM (파서가 다시 돌아도 안 덮어씀). 정정으로 기준서가 바뀌면 LLM 행을 지우고 다시 뽑음
app_user로그인 사용 시작: 이메일 + password_hash(scrypt 해시만 저장). 관리자는 서버 설정으로 구분
company_user업체 등록한 사람 = OWNER · ACTIVE. 가입 때 사업자번호로 기존 업체 합류 요청 = MEMBER · PENDING → 소유자 승인 시 ACTIVE, 거절 시 REJECTED
company본점 소재지는 행안부 도로명주소 검색 결과만 받음 → area_limit·sub_area_code를 서버가 정하고 address_validation_status = MATCH
favorite_notice관심공고 추가·해제 API 사용 시작 (사용자 개인별)
notice_schedule_event일정 저장 시작 (공고 3,218건, 13,145개). 적격심사서류 제출기한은 날짜 없이 원문 문구만 (event_at NULL, confirmed 0)
company_evaluation_draft점수 계산 저장 시작. inputs 키는 배점 행의 position(공고 안 순서) + 공통 키 bid_price·planned_price·management_method, updated_by = 저장한 사용자

evaluation_rule23칸

적격심사 평가 기준: 행 1개 = 공고 1건의 평가 항목 1개 (분야별 배점, 입찰가격 산식, 구간 점수표, 가·감점, 통과점수)
쓰는 모듈: 정근(배점·산식 추출). 산식이 그림에만 있으면 formula_source='IMAGE' + image_path 로 남기고,
LLM이 그림을 읽어 formula 를 채운 뒤 updated_by='LLM' 으로 고친다 (검증 전까지 verification_status='REVIEW').
parameters JSON 형식 (rule_type 별):
FORMULA {"vars": {"A": "a_amount", "기준율": 88}}
TABLE {"rows": [{"min": null, "max": 50, "score": 7}, ...]} 또는 {"rows": [{"grade": "AAA", "score": 15}, ...]}
FIXED {"score": 1, "condition": "원문 조건 문구"}
THRESHOLD {"pass_score": 95}
GROUP 하위 항목을 묶는 행 (예: 당해공사 수행능력 30, 시공경험 18). max_score 가 묶음 한도.
가감점 묶음은 {"min": -5, "max": 0.1} 처럼 범위를 둔다
근거 위치(source_location)는 본문 줄 번호가 아니라 '별표1 > 제3조 > 표 2행'처럼 문서 구조로 쓴다
(재파싱하면 줄 번호가 바뀜). 다시 찾을 때는 source_quote 를 본문에서 검색한다.

SELECT e.company_id, n.notice_no, n.title, n.place_name, n.work_type,
       n.attend_req_close_at, n.bid_end_at, n.presumed_price,
       e.overall_status, e.reason
FROM bid_notice n
JOIN company_bid_eligibility e ON e.notice_no = n.notice_no
WHERE n.company_id_src = 'COM01'
  AND n.purchase_type = 'ConstructionService'
  AND n.bid_type = 'QualifiedEval'
  AND n.is_open = 1
  AND (n.attend_req_close_at IS NULL OR n.attend_req_close_at >= datetime('now', 'localtime'))
